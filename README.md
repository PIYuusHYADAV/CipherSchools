# LLD Practice Platform

A small prototype for practicing Low-Level Design: pick a problem, design a solution,
submit it, get feedback that mixes objective checks with narrative reasoning, and see
your attempt history.

See `RESEARCH.md` for the problem/market research and `DESIGN.md` for the domain design
and evaluation approach in detail. `PLAN.md` is the phase-by-phase plan this was built
against. `AI_USAGE.md` documents where AI was used while building this.

## Running it

Requires Python 3.10+.

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Then open http://localhost:8000

The database is a single SQLite file (`lld_practice.db`) created automatically on first
run, seeded with 3 problems (Parking Lot, Vending Machine, Elevator). Delete the file to
reset all data.

There's no login — every attempt/submission belongs to a single hardcoded demo learner,
which is enough to demonstrate the full loop without building auth.

### Using a real LLM for feedback (optional)

By default, narrative feedback is generated by a rule-based evaluator that reads your
actual submission (no API key needed — the app runs fully offline). To use a real Gemini
call for the narrative half of feedback instead:

```bash
export GEMINI_API_KEY=your-key
export USE_REAL_LLM=1
uvicorn app.main:app --reload
```

Get a key from https://aistudio.google.com/apikey (free tier available).

Both evaluators implement the same `Evaluator` interface, so nothing else changes.

## Running tests

```bash
pytest tests/ -v
```

20 tests covering: the deterministic evaluator's individual checks, the narrative
evaluator's content-sensitivity (different submissions get different feedback), the full
API practice loop end-to-end, and the failure/edge cases called out in the assignment:
malformed submission data, evaluation failures + retry, unknown problems/attempts/
submissions, and multiple submissions on one attempt.

## Project structure

```
app/
  domain.py              # plain domain objects + Evaluator interface (no DB/HTTP)
  models/orm.py           # SQLAlchemy models (Problem, Attempt, Submission)
  evaluators/
    deterministic.py      # rule-based, explainable checks
    mock_llm.py            # rule-based narrative feedback (default, offline-safe)
    llm.py                  # real Gemini-backed narrative feedback (optional)
    composite.py             # merges deterministic + narrative into one result
  seed.py                # the 3 practice problems
  main.py                # FastAPI routes
  templates/, static/    # server-rendered HTML + vanilla JS (no build step)
tests/
  test_evaluators.py       # deterministic evaluator unit tests
  test_mock_llm_evaluator.py  # narrative evaluator + composite tests
  test_api.py                # full end-to-end + failure/edge case tests
```

## Key decisions (short version, full reasoning in DESIGN.md)

- **Evaluation is split into a deterministic evaluator (facts) and a narrative evaluator
  (trade-offs/alternatives)**, merged by a `CompositeEvaluator`. This is the core answer to
  "which parts of evaluation should be deterministic vs. benefit from an LLM."
- **Submission format is structured classes/relationships + optional free-text code**,
  not a diagram canvas — enough structure for objective checks, without the time cost of
  a drawing tool.
- **Evaluation runs synchronously** with a real `pending -> evaluating -> completed/failed`
  status, and failures are caught and shown with a retry button rather than crashing.
- **A monolith, single SQLite file, no auth, no queue.** All out of scope for what this
  assignment is actually evaluating.

## Limitations (being upfront about them)

- **God-class detection is a simple field+method count threshold**, not real cohesion
  analysis. It's an explainable heuristic, not a claim of deep static analysis.
- **Entity-name matching is a case-insensitive substring check**, not NLP - a learner
  using a very different vocabulary for the same concept (e.g. "Bay" instead of
  "ParkingSpot") would be marked as missing that entity even if the idea is present. This
  is a known trade-off of keeping the deterministic evaluator simple and fully explainable.
- **No auth** — single demo learner, intentionally out of scope.
- **Evaluation is synchronous** — fine for the mock evaluator and a single-learner demo;
  see DESIGN.md for how this would change under real load or a slower real LLM.
- **Only 3 problems** — enough to demonstrate the loop, not a full problem bank.
